## 一句话要点

KVMem 将超出模型原生上下文窗口的工作区历史保留为分页 KV 状态，并在 GPU、主机内存和 NVMe 之间虚拟化，以支持百万 token 的长程代理执行。

## 研究对象

- **世界或环境：** 持久化的长上下文代理工作区，历史状态分布在 GPU memory、host memory 与 NVMe；摘要还报告了配备 24 GB RTX 5090 Laptop GPU 的本地部署。
- **智能体：** 长程 LLM agents，实验包含 Qwen3.6/3.8-27B 的本地推理配置。
- **观察与动作：** 代理查询工作区时，model-native attention-space index 选择相关历史块，系统按查询重建受原生窗口限制的 execution view；代理继续执行相应任务。
- **目标与交互协议：** 比较 KVMem 与摘要式 context compaction，在 LongMemEval、MemoryAgentBench、AgentLongBench 和 DeepSWE 等长上下文任务上测量效用、吞吐和延迟。

## 论文做了什么

作者提出分页 KV 状态、轻量索引和 query-dependent materialization，将“已处理过但仍可寻址”的历史与模型当前上下文窗口解耦。系统不把旧历史全部压成摘要，也不必每次重新 prefill 全部文本。

## 证据与发现

摘要报告测试历史最长达 1,000,000 token（约为 256K 原生窗口的四倍）；在 DeepSWE 长上下文测试中，Qwen3.8-27B 的任务成功率从仅压缩的 43.8% 提升到 48.4%。本地配置约 50 token/s，并保持交互式响应。上述数字是作者在指定模型和硬件上的结果。

## 可复用模式

- 将长期记忆的“可寻址容量”和“单次可见上下文”分开；
- 以 attention-space 检索历史块，再按查询构造执行视图；
- 同时报告任务效用、内存层级、吞吐和本地部署成本，而不只报告召回率。

## 局限性与开放问题

结果依赖特定模型量化、GPU/NVMe 配置和 serving stack；KV 状态的迁移成本、崩溃恢复和多代理共享尚未在摘要中量化。论文页面未列出代码仓库，也未直接测试社会模拟或角色一致性。
